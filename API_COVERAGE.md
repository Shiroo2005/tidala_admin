# API reference and demo boundary

The reference is the user-supplied `api-1 (6).json` (OpenAPI 3.1). `src/generated/api.ts` is generated from that exact file. Generated types describe the reference API; they do not imply that the demo connects to it.

The source admin uses older routes and view models. Its services retain those interfaces so the extracted screens and interactions stay consistent. The local adapter returns the response shape each service expects, with no network fallback.

| Area | Reference API | Demo implementation |
| --- | --- | --- |
| Tags | `/api/v1/tags`, CRUD and bulk creation | **Live** (via `liveAdapter`; the fixture note no longer applies). |
| Training levels | `/api/v1/training-levels`, CRUD and bulk creation | **Live** (via `liveAdapter`; the fixture note no longer applies). |
| Provinces and districts | `/api/v1/provinces`, `/api/v1/districts` | **Live** (via `liveAdapter`; the fixture note no longer applies). |
| Posts | Admin list/detail/status, post deletion | **Live.** List, search, category filter and detail use `/api/v1/admin/posts` (filtered and paged locally, since the admin list has no keyword/category filter); deletion uses the admin delete. Pinning has no endpoint and is refused. |
| Reports | Teacher/review reports and resolution | **Live.** Teacher and review reports, detail and per-user history. The report payload carries the reporter's id and email; the reporter's name and avatar are resolved from the admin user list, and the reporter cell (tables, cards and the detail overview) has a detail button that opens the reporter's account (role, status, contact, join date, report counts, and ban state/reason when banned) resolved from the same list, since there is no get-user-by-id endpoint. `DISMISSED` is shown as `REJECTED`; the post tab and the "reviewing" filter are always empty. Reasons map to the closest UI reason. Resolving goes through `POST /reports/{id}/actions`: ignore → `DISMISS`, warn → `WARN`, hide → `REMOVE`, timed ban → `BAN` (1–365 days; permanent bans are refused). The detail shows the backend's action log as history. |
| Teachers and students | Public teacher profiles; admin user list and ban/unban (`/api/v1/admin/users`, added by the updated reference `api-1 (6).json`) | **Teachers live, read-only.** List and detail come from the public directory (completed profiles only, no email/phone/account status; every listed teacher shows as active). Reviews and rating summary are live. Invite, profile edit and sanctions on teachers are refused. **Students live.** The student list comes from `GET /api/v1/admin/users?role=STUDENT` (search, status, sort and pagination are applied locally, since the endpoint has no status filter and no get-by-id). Ban/unban map onto `POST /api/v1/admin/users/{id}/ban` and `/unban`: a suspension uses the chosen duration, a permanent ban maps to the 365-day API maximum, and warnings are refused because the backend has no warning mechanism. A timed ban does not change the stored account status, so banned students are recognised by the `banned`/`bannedUntil`/`banReason` fields. Dashboard user counts are now computed from the same admin user list. |
| Dashboard | No matching admin statistics endpoints | Statistics are calculated from the local database, with period filters and updated counts after mutations. |
| Authentication | Login, current user, refresh, logout | **Live.** Email/password login, `/auth/me`, token refresh and logout against the backend; non-admin accounts are rejected. No OAuth. |
| Uploads | `/api/v1/image-uploads` | Still local. Its only consumer, teacher profile editing, has no admin endpoint. Backend images are shown from `VITE_IMAGE_URL_PREFIX` (default `https://cdn-dev.tidala.vn`). |
| Address autocomplete | No matching autocomplete API | Local driving-center suggestions and deterministic demo coordinates. |
| Settings | No matching settings API | Retains the existing simulated controls. |

**Update:** Authentication, tags, training levels, provinces/districts, posts, reports, teachers (read-only) and students now call the reference API through `src/config/liveAdapter.ts` and `src/config/live/`, which translates the screens' older request/response shapes. Tag bulk-create issues one POST per tag, since the reference API has no bulk tag endpoint. Address autocomplete, uploads and settings are still demo-only. For the rest, live integration is a separate task: implement adapters for the reference schemas and obtain missing admin APIs before connecting the legacy features. Do not simply replace the demo adapter with a network base URL.

**Reference updated (2026-10-16):** `references/openapi.json` is now the user-supplied `api-1 (6).json`, which adds the admin user-management family (`/api/v1/admin/users` + ban/unban), `/api/v1/admin/notebook/students`, audit logs and post pin/delete. `src/generated/api.ts` was regenerated from it; the only fallout was the demo training-level fixtures, which now carry a `progressTemplate`, and one schema-conformance assertion that now skips `$ref`-typed properties (it still checks that every fixture key exists in the schema).
